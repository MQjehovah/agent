## 一、项目背景

1. **员工高频重复协调工作**（设备运维、售后工单、代码审查、IT/CI/CD、报表、知识查询）
   跨 Jira/钉钉/文档/笔记等多系统，靠人工协调耗时、响应慢、经验留在个人。
2. **大模型能力多供应商并存**：缺少统一入口与治理，无法按员工计量/配额/审计。
3. **企业内部知识分散**，缺乏统一检索入口；已有能力(代码审查等)分散在试点工具里。
4. **现状差距**：`agent` 执行引擎功能已很强(工具/技能/子代理/团队/记忆/自学习)，但
   仍偏“单实例单用户”试点形态，面向“全公司共用”还缺：**企业身份、多用户运行隔离、
   全程审计、管理员可观测、可靠运维** 等工程化底座。
5. 平台层面已规划 5 子系统(dashboard/agent/rag/router/market)；本项目的范围是把
   **agent 从“执行引擎”演进为“可放心服务全公司的在线智能体服务”**，并接入网关身份。

## 二、项目价值

| 价值 | 说明 | 可度量 |
|---|---|---|
| 提效 | 处理跨系统重复/协调工作，缩短响应 | 任务处理工时、平均响应时长 |
| 7×24 | 在线值守，随时响应员工请求 | 服务可用性(≥99.5%) |
| 知识沉淀 | 记忆/经验/技能可复用，个人→组织 | 记忆条目、技能复用次数 |
| 成本透明 | 按员工/部门计量与配额 | token/费用归集准确率 |
| 合规可信 | 全程可审计、权限隔离、可回退 | 审计落盘率 100%、越权事件=0 |
| 生态可扩 | 能力市场/rag/router 统一接入 | 接入能力数 |

## 三、项目目标

### 3.1 总体目标
把 agent 建设为**全公司员工可同时使用、按人隔离、全程审计、管理员可观测、
可可靠运维的在线 AI 助手**，作为零号员工平台的执行引擎对全员开放。

### 3.2 分级目标
- **G1 · 可用(试点)**：单集群内 N 名试点员工可稳定并发对话、工具/子代理可用、
  会话可续聊、过程可视化。
- **G2 · 可管(全员)**：全员规模(100+ 并发)；按用户/角色隔离(会话/记忆/文件)；
  全量审计与用量；管理端可观测大盘；企业 SSO 身份接入。
- **G3 · 可靠(生产)**：备份/恢复、灰度回滚、容量保护与限流、指标告警、可扩展部署。

### 3.3 关键指标(验收基线)
| 指标 | 目标 |
|---|---|
| 并发 | 支持 ≥100 同时会话(压测口径)，单用户多会话不乱串 |
| 首包延迟 | P95 首 token ≤ 2s(网络+模型链路) |
| 上下文 | 长会话自动压缩，P50 token/请求 可观测 |
| 隔离 | 越权访问事件 = 0；跨用户文件/记忆泄漏 = 0 |
| 审计 | 会话消息落盘率 100%；查询/导出可用 |
| 恢复 | 进程/worker 重启后对话上下文可恢复(RPO≈0 数据, 任务续跑) |
| 可观测 | 实时会话/在线/用量/性能 P50·P95 大盘可用 |

## 四、范围与边界

**做**：agent 执行引擎的企业化 —— 身份与隔离、对话模型、审计、用量、
管理可观测、worker/容量、可靠性、Web UI 体验、工程化(测试/文档/部署)。

**不做(依赖其它子系统)**：不实现统一 SSO 服务(sso/)、桌面端(dashboard)、
算力计量网关(router)、知识存储(rag)、能力上架审核(market)——按平台边界对接。

## 八、里程碑路线（建议）
- **M1**：worker 池默认开启+容量守护；SSE ask/审批；限流配额；webhook DB 化续跑。
- **M2**：拆 server/core 为域+Service、run 语义收敛；修测试补 e2e；安全基线(默认口令/secret)。
- **M3**：多实例部署+指标告警+备份恢复制度；审计导出闭环；与 router/rag/market 计量打通。

## 九、风险与应对
| 风险 | 应对 |
|---|---|
| 单进程容量/单点 | worker 池+容量守护 → 多实例/横向(P2) |
| worker 内存放大 | 每 worker 完整 Agent 初始化；压测定容量、空闲回收 |
| 默认隔离未开 | 公司部署默认开启 + 文档/启动检查 |
| 测试集损坏 | 修测试引用/补 e2e(列入 M2，先保关键路径) |
| SQLite 单库 | 备份制度、WAL；远期按会话/用量分库或上托管 DB |
| 交互短板 | SSE 双向 ask/审批列入 P1 |
