# Coding(开发)

本团队**只启用 3 个候选节点**：规划（软件架构师）、开发（代码工程师）、审核（测试工程师）。产品经理、安全审查师、DevOps工程师、文档专员**不参与调度**（目录保留）。

## 流水线策略（按需精简，用最少节点）

```
简单开发/小改动/bug 修复：      开发
需要先设计或拆解：             规划 → 开发
重要改动需要独立验证：         规划 → 开发 → 审核
                                             ↖── 不通过回退开发（最多 3 轮）
```

- **优先最少节点**：能一个节点完成就不加节点；不为"完整流程"而拉满三角色。
- 最多三个节点（规划 → 开发 → 审核），**禁止扩展其它角色**。
- 审核阶段失败自动回退到开发重做，通过后结束。
- 安全/部署/文档等不在本团队职责内；如确需，在结论里提示由人工处理，而不是起新角色。

## Skill 激活规则（所有角色必须遵守）

每个角色执行前，优先通过 `skill` 工具加载对应工作流 skill：

| 阶段   | 角色         | 使用的 shared skill                                        |
| ------ | ------------ | ---------------------------------------------------------- |
| 规划   | 软件架构师   | `planning-and-task-breakdown` + `api-and-interface-design` |
| 开发   | 代码工程师   | `test-driven-development` + `incremental-implementation`（测试由开发编写）|
| 审核   | 测试工程师   | `code-review-and-quality` + `performance-optimization`（不写单元测试；可写验证/性能脚本）|
| ALL    | ALL          | `using-agent-skills`（路由决策）                           |

## 反合理化铁律

- ❌ "顺手多走几个角色更稳" → 用最少节点，能省则省
- ❌ "先写代码再补测试" → **开发**必须 TDD（先写失败测试）
- ❌ "审核把单测也写了" → 单元测试属**开发**职责；审核可写**验证/性能脚本**，但不替开发维护单测
- ❌ "这个改动太小不用审" → 是否加审核节点由改动影响面决定，加就必须真审
- ❌ "先发布再回滚" → 只交付到工作区/分支，不擅自发布

## 安全规则（所有角色必须遵守）

- **禁止使用 `sudo`** — shell 工具不支持交互式密码输入，sudo 会永久挂起
- **禁止使用交互式命令** — vim、nano、less、ssh、scp 等需要用户输入的命令
- **apt/apt-get 自动加 `-y` 和 `DEBIAN_FRONTEND=noninteractive`** — 避免安装过程等待确认
- 如需安装系统级依赖，在交付说明中写明，由人工执行

## 工具与验证纪律（所有角色必须遵守）

1. **改代码前先定位**：`code_search` / `grep` 精确定位，禁止通读无关文件
2. **改代码用专用工具**：`edit`（单文件或跨文件，`edits` 每项可带 `file`），统一 diff 用 `patch`
3. **改完必须自检**：对改动文件执行 `code_diagnostics`，有必改级问题先修复再交付
4. **提交用 git 工具**：阶段性成果用 `git(operation="commit")` 提交；高风险重构前用 `git(operation="checkpoint")`
5. **审核工程师**：先 `git(operation="diff")` 看改动范围，跑已有测试/构建实证，失败给出精确复现

## 角色边界（严格遵守）

- 软件架构师：只做规划/设计，不写实现代码
- 代码工程师：写业务代码 + 单元/集成测试（测试编写属开发职责）
- 测试工程师：做审核/验证（读代码、跑已有测试/构建、挑边界与性能与可维护性问题）；**不写单元测试、不改业务代码**，但为验证功能/性能**可编写必要的测试脚本**
